## Unreleased

- A T order can now name a **defenceless** building or airship, and an unarmed carrier can give that order. Vanilla writes "is this target worth shooting" as `dangerCache > 0`: the order branch of `Module.targetShip` is `if (this.ship.fireAt != null && this.ship.fireAt.dangerCache > 0.0 && …)` (line 1464), `Module.target` repeats the test when it keeps last frame's aim (line 1664, `prevTargetShip.dangerCache > 0.0`), and `dangerCache` comes from `Airship.danger(c)`, which returns 0 outright when `!inCombat(c)` — which is exactly an unarmed immobile building (or an airship that lost its guns and propulsion, or its whole crew). The named target was therefore skipped in silence and the guns went back to their own automatic targets. ARC replaces only those judging reads, handing vanilla "the real value, or an equivalent positive 1.0 when this is the target the player named". Both automatic paths (the `dangerCache / (dist + 100)` ranking at the end of `targetShip`, and the two fallback loops in `target`) are untouched, so ships and aircraft never engage a defenceless target on their own — someone has to name it with T. Direct control is unaffected because it aims through `prevTarget` and never consulted `dangerCache`; weapons with `destroySuspendiumInRadius` still obey the original suspendium condition.
- An unarmed carrier could not even send that order: in a multi-selection `TargetCommandTool.click` requires `s.canShoot()` before sending `fireAt` (line 94), so a weaponless carrier was filtered out and only the armed ships in the box received the order. The panel's T button was drawn from `anyShipsReady && anyShipsCanShoot` (line 570, with `anyShipsCanShoot` fed by `s.canShoot()` on line 291) and therefore stayed grey for a weaponless ship. All four places now ask "has guns, or can hand the order to aircraft": `canShoot() || canGiveAircraftCommands() || hasFlyers()`.
- That last test must **not** rely on the flight centre alone: `canGiveAircraftCommands()` is driven by `ModuleType.canGivePlaneCommands`, and only `FLIGHT_CENTRE` declares that key in the game's data. The hangars (`BOMBER_HANGAR`, `BIPLANE_HANGAR`, `TRIPLANE_HANGAR`, `TORPEDO_BOMBER_HANGAR`, `ROCKET_PLANE_HANGAR`, `GATLING_SKYBOAT_HANGAR`) declare only `quartersType` (whose `CrewType.canFly` is true), so a carrier built from hangars without a flight centre reads false there — its T button stayed grey even though its aircraft launch and inherit the mothership's `fireAt` exactly the same way. ARC now uses the vanilla `Airship.hasFlyers()` (any module whose `quartersType.canFly` is true) so those carriers count too; a transport with neither guns nor aircraft bays is still skipped as in vanilla, and a cooling-down ship never lights the button up.
- The aircraft side of the same order was blocked by `dangerCache > 0` too (`Crewman.outsideShootingTick`, line 2248), and the same method wipes its target every tick (line 2239, `this.attackTarget.dangerCache <= 0.0`). That wipe happens before the reload early return (line 2245) while the carrier's order is inherited after it, so relaxing line 2248 alone would leave a reloading aircraft with no target at all and throw away the whole attack run; both reads are changed so a launched aircraft keeps chasing the defenceless target its carrier named. Automatic target picking (lines 2251-2267, still `dangerCache > 0`) is unchanged.

- Keep aircraft attack runs on target: an aircraft's strafe aim point is now stored relative to its target instead of as a fixed world coordinate. The native `Crewman.outsideFlyingTick` locks exactly one world point per attack run (`strafeTo` = the target's far edge ± `strafeOvershoot`, chosen by comparing the aircraft's centre with the target's centre) and throws that point away as soon as the target's box moves `2 × strafeOvershoot` (400 px) away from it — one of four discard conditions on the same line. The point is then re-chosen purely from "which side of the target am I on right now", so a target that drifts while the aircraft is still approaching can put the new point behind the aircraft, and the aircraft turns around instead of finishing its pass. A bomber pays the most for that turn: its `airXAcceleration` of 0.00008 is the lowest of the five aircraft (6.25 s and 391 px of skid to reverse at minimum speed, 15 s from top speed), and it must fly a straight line through the middle 60% of the target to release anything (the `bombs` drop test), so an interrupted run deals no damage at all. ARC now translates the stored aim point by the target's own per-frame movement, which keeps the target-relative offset exactly constant and leaves the turn-around decision to the moment the aircraft actually reaches the point. A target switch (the carrier's `fireAt`, or re-acquiring the nearest ship after a kill) and a save load re-anchor without shifting, so a new target is still decided by vanilla; the no-target patrol branch, ground crew and non-flying units are untouched. Measured with a standalone model of the native method (60 s runs, 5 samples per target speed): attack runs that end without a release drop from 1.8–19 per minute to zero at every speed, and releases against a target closing at 0.20 px/ms go from 2.2 to 12.0. One trap for anyone extending this: `com.zarkonnen.catengine.util.Pt` is immutable *and* its `shifted()`/`towards()`/`between()`/`scaled()` helpers are unimplemented stubs that throw at runtime, so the shifted point has to be rebuilt with the public constructor.

- Add **AI fleet control**: a new *ARC Overhaul: AI fleets* screen (conquest setup → bottom of the settings list, or MOD list → ARC Overhaul → Details) lists every AI fleet the game has loaded and gives each one three states — **Allow** (may be picked at random, vanilla), **Force enable** (reserved and handed to exactly N non-player countries) and **Force disable** (never used). An AI fleet is one `ConstructionStrategy`: it decides which ships, landships, buildings and techs an empire uses. The native game picks one per empire with `ConstructionStrategy.forCharge(charge, difficulty)` + `r.nextInt(size)`, filtered only by heraldic charge and difficulty, with no player control at all. ARC now chooses that fleet itself at the exact call site inside `WorldMap$2.run`, before the `Empire` is constructed — the hook has to be there because `Empire.constructionStrategy` is `public final` and cannot be replaced later. Rule semantics: a force-enabled fleet is removed from the random pool as well, so "3" really means exactly three countries; a banned fleet never appears; the player's own country is never replaced; if every candidate ends up banned or reserved ARC keeps the vanilla pick instead of failing generation. With default settings the method returns before touching anything, so no random draw is consumed and a given seed still produces the vanilla world. Settings live in `game/config/arc_overhaul/conquest-fleets.json` and only non-default entries are written.
- Add **Force disable all** and **Force enable all** buttons to the AI fleet screen: one click marks every loaded fleet, and "force enable all" keeps each fleet's current country count (or its last valid one) instead of resetting it. The box is also nudged down by a small spacer so it lines up with the buttons beside it instead of sitting at the top of the row. (1) The count box looks identical whether or not it can be typed into, because the framework canvas adapter (NativeUiCanvas.text) ignores its enabled flag when painting glyphs, and it deliberately escapes square brackets so a MOD cannot inject the game's rich-text colour codes; painting inactive text grey is a one-line framework change. (2) Restoring the deleted number when you click into another box without typing needs a focus-lost notification, and UiRuntime currently changes focus with no callback. ARC instead restores empty boxes on the next thing you do — typing in any other box, pressing any button, or Apply — and never writes a 0. Before touching the framework, note that its source tree is at 0.3.3-dev.33 while the built and installed API jar is 0.3.3-dev.21, so a rebuild would also land dev.22-dev.33 in the game.

- Fix extra starting towns losing their territory colour on the strategic map. Skipping unused placement slots left gaps in the native settlement ID sequence, and the native territory tracer (`ShapeUtils.cityOwnershipAreas`) walks IDs upwards from 0 and exits permanently at the first ID with no owning cell — so every settlement above that gap never received a territory area and was never painted. Settlement IDs are now assigned contiguously as they are created. When no placement slot is skipped the sequence is identical to vanilla, so maps using the default counts are unaffected.
- Add a **Player starting research points** field (0–10,000,000, default 0 = vanilla) to the ARC starting options. The value is banked into the native *unassigned* research pool (`Empire.unassignedResearchPoints`), which the game pours into the first research the player selects. Granting it through `Empire.researchPoints` does not work: the native set-research command (`CampaignWorld`, bytecode 223–312) overwrites that field with the new tech's partial progress before adding the pool, so the grant was silently discarded on the first click. The range is in the millions because a technology costs `BASE_RESEARCH_COST × RESEARCH_COST_MULTIPLIER × 5600 × 1.4^tier` points (`Tech.baseCost`) — measured in-engine as 1,680,000–2,352,000 for the first tiers; a smaller grant is invisible on the progress bar. The probe asserts the range stays within scale of a real technology. Grantee timing is identical to the existing cash grant (same CREATED callback, same loop) and the grant is logged.
- Keep ARC-added settlements off isolated land. The native spot finder `WorldMap.findMapLocationSpot` only requires the candidate tile to be *not water*, so a single land tile surrounded by sea is a valid result and an added town could be generated on a speck connected to nothing. ARC now wraps that call for human empires and re-rolls until the tile belongs to a connected landmass of at least `max(32, gridSize/4)` tiles; the retry budget is bounded and falls back to the last candidate, so the guard cannot turn generation into a failure. AI empires and default settings keep the untouched native result. Verified with an A/B probe: the unguarded native finder places a settlement on an isolated island for 6 of 16 seeds, and with the guard the same seed lands on real land.

- Report landship speed with its **ground friction**. The native panel speed (`ShipEditorUtils.getStats` → `Airship.getMainMapSpeed` → `getSpeed`) subtracts only quadratic air drag, but every grounded spring also damps horizontal speed by `(1 - Spring.xFriction × fMult)` **per tick** (`Module.java:679-684` for tracks, `Leg.java:299-304` for legs; `ModuleType` hard-codes 0.002 for module springs and 0.004 for leg springs). Airships have no springs, which is why only landship numbers were wrong. ARC now solves the real steady state `F/m = f·v² + λ·v` over air friction plus ground friction and reports that value, so the editor, strategic screen and combat panel all show the speed the ship actually reaches. Measured in headless combat (flat ground, full throttle, direct control, no terrain contact): a Medium-Legs walker reaches 0.235 against the 0.690 the old panel claimed (34 %), Large-Tracks 27 %, Tracks 16 %, while a springless airship keeps the native value. Gameplay is untouched: AI, strategic-map movement and the `engineForceForX` braking simulation still use the native formula.
- Validation for the ground-friction report: game 1.2.15.2, **438 checks pass** with API `0.3.3-dev.21` (the 426 existing checks plus 12 new ones: real mixin transformation on `ShipEditorUtils`, the native per-tick decay rule, the λ solve, spring collection for landships versus airships, and the panel value being strictly lower). Test game 1.2.14 was not re-run here.
- Ground friction now scales with the load actually resting on the ground, so **lift finally makes landships faster**. The native friction is a constant factor applied whenever a spring is compressed (`Module.tick`, `Leg.tick2`) and ignores how much of the ship's weight reaches the ground. Turtle-shell armour (`SHELL_ARMOUR`, `"lift": 35` per tile; `Airship.getLift()` sums armour lift alongside module lift) and suspendium therefore did nothing for a landship's speed: measured in a headless combat with the real game data, re-armouring a Strider with 27 turtle-shell tiles gives 945 lift against a mass of 1008 (more than enough to hold the ship up), yet the measured ground-friction rate stays at 0.00476 versus 0.00499 for the bare hull, and the extra armour weight only makes the ship slower. ARC now scales the friction coefficient by `load = clamp((weight − lift) / weight, 0, 1)`, where the lift is `Airship.availableLift(combat)` inside combat (so destroyed armour and unpowered chambers stop counting) and the design value `getLift()` on the panel. Ships without lift have `load = 1` and keep bit-for-bit vanilla behaviour; airships and buildings are untouched.
- Validation for the load-scaled friction: game 1.2.15.2, **544 checks pass** with API `0.3.3-dev.21` (the 529 existing checks plus 15 new ones: the load-fraction maths, real lift flowing from fabricated turtle-shell armour through `getLift()`, the friction base staying unchanged at load 1 and halving at load 0.5, the panel rate matching the physics factor, and the injector being present on the real `Module` and `Leg` classes). The isolated harness has no ship-data directory, so the resulting speed increase was not measured inside it; the vanilla shortfall it corrects was.
